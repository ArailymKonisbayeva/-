# Аккаунты и администрирование «Әдеби саяхат»

## Обновление 23 октября: регистрация без письма

По запросу владельца сайт теперь входит сразу после регистрации, **если Supabase вернул настоящую сессию**. В Dashboard откройте Authentication → настройки Email provider → выключите **Confirm email** и сохраните. Этот переключатель нельзя изменить публичным ключом; в коде сайта его выключение не заменяет настройку сервера. Если письма пока обязательны, сайт сообщает об этом, не создавая фиктивной сессии.

Новая SQL-миграция не нужна: при отключённом Confirm email Supabase сам устанавливает `email_confirmed_at`. Проверки действительного пользователя, RLS, блокировки и таблица `private.admins` сохранены. Эта отметка больше не доказывает владение почтовым ящиком. Администратора назначайте только по проверенному UUID своего аккаунта, не по заявленному email. Совпадение email не даёт административных прав.

Перенос старых данных по email отключён и в интерфейсе, и в методе импорта. Старые прогресс-записи не удалены. Разделы ниже о включении Confirm email и самостоятельном legacy-импорте описывают прежний режим и больше не применяются. Существующим неподтверждённым аккаунтам может потребоваться отдельное подтверждение; не удаляйте их для повторной регистрации. Восстановление забытого пароля по-прежнему требует письма и SMTP. Проверка нового режима: `node tests/signup-mode.cjs` (модульный тест, без реальной регистрации).

## Что обнаружено и изменено

Сайт — статический HTML/JS, без backend и БД. Старый `auth.js` сравнивал email и открытый пароль из `adebiet-user` в localStorage. Прогресс был частично общим для браузера, частично привязан к email. Такая запись **не является настоящим аккаунтом**.

Теперь единственный источник авторизации — Supabase Auth. PostgreSQL хранит `profiles`, `user_progress`, `user_achievements`. `auth.users.id` — первичный идентификатор. Пароли не записываются в эти таблицы или код приложения. SDK хранит сессию (токены, не пароль) в браузере. Старый открытый пароль удаляется из localStorage при первом запуске новой версии; остаётся только email для предложения переноса. Старые пароли не отправляются в Supabase и не мигрируются.

Все произведения, обложки, игры, квесты и добавленная ранее «Қар қызы» сохранены. UI регистрации использует прежние классы оформления. Добавлены никнейм, подтверждение email, восстановление пароля, сообщения ошибок, профиль и админ-панель. До настройки реального проекта вход отключён: демонстрационного обхода нет.

## 1. Создать проект и применить миграцию

1. В Supabase Dashboard создайте проект, сохраните пароль БД в менеджере паролей. Не присылайте его и secret/service_role key в чат.
2. Сначала используйте отдельный staging-проект. В SQL Editor выполните целиком `supabase/migrations/202610220001_accounts.sql`. Она транзакционная и предназначена для однократного применения. При существующих одноимённых таблицах остановитесь и согласуйте схему, не удаляйте их.
3. Проверьте три таблицы в Table Editor и включённый RLS. Схема `private` содержит роли администраторов и журнал экспорта/блокировок. **Не добавляйте private в exposed schemas Data API.**
4. В Settings → API / API Keys скопируйте Project URL и **publishable key** (`sb_publishable_…`). Допустим также legacy `anon` JWT. Secret и `service_role` во frontend запрещены; генератор конфигурации их отклоняет.

## 2. Настроить email Auth

В Authentication:

- Включите Email provider, регистрацию и **Confirm email**. Минимальная длина пароля — 12 (настройте и на сервере, HTML-проверки недостаточно). Отключите anonymous sign-ins, если они не нужны.
- URL Configuration → Site URL: реальный HTTPS-адрес сайта с корректной подпапкой.
- Redirect URLs: точные адреса `https://ВАШ-ДОМЕН/ПОДПАПКА/index.html` и `http://127.0.0.1:8000/index.html` для разработки. При GitHub Pages учитывайте путь репозитория `/-/`. Не используйте широкие production wildcard.
- Email Templates: ссылки подтверждения и восстановления должны использовать Supabase `ConfirmationURL`, не самостоятельный hash-маршрут приложения. Возврат идёт в `index.html`; SDK обрабатывает токены до входа в приложение.
- Настройте собственный SMTP, sender, SPF/DKIM и проверьте доставку. Встроенная почта ограничена и не предназначена для публичного production. Отключите в почтовом сервисе link tracking, если он портит auth-ссылки.
- Настройте rate limits; перед публичным запуском рассмотрите CAPTCHA и MFA. В текущей версии MFA/CAPTCHA интерфейс не реализован; включение обязательного challenge потребует его интеграции.

Дубли email обрабатывает Supabase Auth. Ответ регистрации намеренно нейтральный: нельзя использовать форму для перечисления существующих аккаунтов. Никнеймы в этой версии не уникальны.

Официальные инструкции: [парольный вход](https://supabase.com/docs/guides/auth/passwords), [SMTP](https://supabase.com/docs/guides/auth/auth-smtp), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [привилегии функций](https://supabase.com/docs/guides/database/functions).

## 3. Настроить frontend

Скопируйте `.env.example` в `.env`, заполните только URL и публичный ключ. `.env` исключён из Git. Node.js 20.6+:

```powershell
node --env-file=.env scripts/configure-supabase.cjs
```

Генератор создаёт `supabase-config.js` только с двумя публичными параметрами. Альтернатива — заполнить эти два значения в файле вручную. Статический сайт не умеет читать `.env` самостоятельно. Опубликуйте публичный конфиг вместе с сайтом; `.env`, SQL-тестовые пароли, папки `.git` и серверные секреты не публикуйте. Не запускайте весь репозиторий как публичный production файловый сервер. Локальный `local-server.ps1` слушает только loopback; перезапустите его для новых правил `/admin` и запрета приватных путей.

SDK закреплён на `@supabase/supabase-js@2.57.4` и загружается через jsDelivr ESM. Нужен доступ к CDN и вашему Supabase endpoint. Сессии используют implicit flow, подходящий для этого browser-only сайта, без cookie-сервера. Это не SSR-приложение. Сторонние скрипты не должны быть недоверенными; XSS может украсть browser-сессию. Перед production настройте CSP с учётом старых inline обработчиков сайта и хостинга.

## 4. Назначить первого администратора

Зарегистрируйте свой реальный аккаунт через сайт и подтвердите письмо. Скопируйте UUID из Authentication → Users. Только в SQL Editor под владельцем проекта:

```sql
insert into private.admins(user_id) values ('UUID-ПОДТВЕРЖДЁННОГО-ПОЛЬЗОВАТЕЛЯ');
-- Отозвать права:
-- delete from private.admins where user_id='UUID-ПОЛЬЗОВАТЕЛЯ';
```

Войдите заново. Панель доступна по `/admin/` (или `/-/admin/` на GitHub Pages) и `index.html#admin`; ссылка появляется в профиле. Сам URL не является защитой: каждое действие проверяет роль на стороне БД. Пользователь не может изменить роль через metadata, profiles или публичный API.

Панель: число зарегистрированных, поиск, сортировка по дате, постраничные аккаунты, индивидуальные произведения/игры/квесты/XP/достижения, CSV. Экспорт ограничен 1000 аккаунтами на запрос, учитывает текущий поиск, предупреждает о персональных данных, защищает CSV от формул и записывается в `private.admin_audit`. Общий счётчик включает неподтверждённые регистрации.

Безопасное управление в приложении — блокировка/разблокировка; свою запись блокировать нельзя. Блокировка немедленно запрещает чтение и запись прогресса через RLS/RPC даже с ещё действующим JWT. Она не удаляет Auth пользователя или ранее загруженные данные с устройства. Удаление аккаунта выполняйте отдельно в Authentication → Users, после проверки UUID и требований хранения; каскад удалит профиль, прогресс и достижения. Это необратимое действие. Роли и audit не доступны через клиентский API.

## 5. Синхронизация и перенос старых данных

- Feature-модули используют `UserStorage`. Кэш разделён по UUID; до проверки настоящего пользователя данные не выдаются. Секреты и auth-записи не входят в progress.
- Значения ключей сохраняются в JSONB (`user_progress`) с версией. Сохранение после ~700 мс, повтор при восстановлении сети и периодически. Индикатор показывает ошибку, а не ложное успешное сохранение. Место чтения, словарь, избранное, результаты игр, квесты и XP используют этот слой.
- На другом устройстве вход загружает серверные значения. Если два устройства изменили один ключ, сервер отклоняет старую версию. В профиле «Қайшылықты шешу / бұлттан жаңарту» сначала скачивает резервную JSON-копию локального состояния, затем принимает облачную версию. Автоматического объединения конфликтующих массивов нет. До разрешения конфликта очередь может оставаться несохранённой; не удаляйте кэш браузера.
- Достижения записывает серверный trigger по учебному прогрессу. Игровые баллы по-прежнему вычисляет существующая клиентская игра: это не античит и не серверная аттестация. Пользователь технически может подделать собственный учебный результат; чужой — нет. Импортированные записи также недоверенные. Не используйте эти данные для денежных наград/экзаменов без серверной валидации игрового процесса.
- Для старого браузера создайте настоящий аккаунт с тем же email и подтвердите письмо. В профиле появится отдельный импорт с повторным вводом **нового Supabase-пароля**. Переносятся только email-scoped ключи этого браузера, только если облачного ключа ещё нет. Старые общие XP/избранное не импортируются: их владельца нельзя надёжно определить. Оригинальные прогресс-записи остаются локально.
- Старый localStorage нельзя криптографически атрибутировать. Повторный вход подтверждает принадлежность нового email-аккаунта, а не подлинность прошлых игровых баллов. Данные других устройств недоступны; автоматический перенос не обещается.

## 6. Проверки перед запуском

Локально:

```powershell
node tests/accounts-unit.cjs
node tests/reader-data.cjs
node tests/reading-sources.cjs
node tests/kar-kyzy-data.cjs
node tests/curriculum-data.cjs
```

Реальная staging-БД: создайте и подтвердите два обычных аккаунта и администратора. Заполните `TEST_*` в локальном `.env`, затем:

```powershell
node --env-file=.env tests/supabase-live.cjs
```

Скрипт проверяет вход, чтение своего профиля, запрет чужих данных, изменение защищённых колонок, запрет прямой выдачи достижений, version conflict, новый вход и восстановление прогресса, админский список/детали/экспорт, выход. Он создаёт тестовую progress-запись и audit экспорта; используйте staging. Без параметров печатает SKIP, не PASS.

Дополнительно выполните `tests/supabase-rls.sql` в staging SQL Editor. Он создаёт временные тестовые аккаунты внутри транзакции, переключает роли, проверяет RLS/RPC/блокировку и делает ROLLBACK. Этот SQL-тест подготовлен, но в текущем окружении без PostgreSQL не запускался.

Обязательные ручные E2E:

1. Регистрация нового email → письмо → подтверждение → вход; повторная регистрация не создаёт второй аккаунт.
2. Неверный пароль/неподтверждённая почта не дают вход. Перезагрузка восстанавливает сессию. Выход закрывает профиль.
3. «Құпиясөз ұмытылды» → письмо → форма нового пароля → выход → вход новым паролем. Истёкшая/использованная ссылка даёт ошибку.
4. На устройстве A завершить произведение, игру, квест; открыть читатель и сохранить слово. Дождаться «Бұлтта сақталды». На B войти и сверить прогресс/достижения. Выйти, войти другим аккаунтом — данные A не видны.
5. Отключить интернет, изменить прогресс, включить сеть. Проверить retry. На A/B изменить одинаковый ключ, убедиться в явном конфликте и резервной копии при разрешении.
6. Обычным пользователем открыть `#admin`, вызвать RPC вручную — отказ. Попробовать update suspended/created_at, insert badge, select чужого UUID — отказ/пустой набор.
7. Администратором проверить поиск, сортировку, страницы, детали, CSV. Заблокировать тестового пользователя — доступ к прогрессу запрещён; восстановить — возвращён. Отозвать роль SQL-командой — последующие admin RPC запрещены.
8. Повторить литературные/читательские browser-тесты с реальными тестовыми аккаунтами. Старые тесты, которые подделывают `adebiet-user`, больше не являются валидным входом.

## Статус поставки

### Публичный счётчик регистраций

Дополнительно выполните в SQL Editor только `supabase/migrations/202610220002_public_reader_count.sql`. Первую миграцию повторять не нужно. Новая функция возвращает ровно одно число из Auth, включая неподтверждённые и заблокированные регистрации; доступа к аккаунтам она не предоставляет. Счётчик виден на главной и на экране входа. Значение запрашивается при появлении блока (не чаще раза в минуту) и при восстановлении сети. Последнее успешное число и время сохраняются в этом браузере отдельно от приватного прогресса. При ошибке сохраняется старое число с датой обновления. На новом браузере без сохранённого значения отображается сообщение, а не выдуманный ноль. Проверка: `node tests/reader-count.cjs`.

Код, миграция и тесты подготовлены. Реальный Supabase проект не предоставлен: миграция не применена к удалённой БД, SMTP/письма, реальный Auth, RLS и admin RPC пока не проверены на вашем сервере. Без Dashboard-настройки это **не введённая в эксплуатацию система**. Не выкладывайте эту версию вместо рабочего сайта до выполнения staging-проверок.
